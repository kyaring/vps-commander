## 一、目标与范围

目标：在不破坏现有生产（Hub 运行版本 943680bec6d1f15d）的前提下，提升 Agent 使用 vchub 的正确率与安全性，并把发布流程做得可回滚。

范围内：
1. Agent 说明层：服务器 instructions、工具 annotations、元数据契约测试。
2. 令牌与参数的 fail-closed 修复（审计报告 P1-1、P1-2）。
3. 执行前确认机制（先设计，后实现）。
4. 客户端 skill 的边界说明。
5. 部署脚本与主密钥分盘（需 OPC 批准生产变更）。

范围外（本计划不做）：
- SSH 凭据托管（vchub 为 agent 模式，不需要）。
- 跳板机、搜索降级（需求不成立）。
- 直接替换或升级生产以外的组件。
- DevTask 主干的合并（由 DevTask 自身的审核流程决定，不在本计划内）。

## 四、需要 OPC 决定的事项

- D1：令牌设备列表解析失败时，该令牌是否立即失效（fail-closed）？建议：是。
- D2：MCP 参数 JSON 非法时，是否改为返回 invalid params 错误（不再静默执行）？建议：是。此变化会让部分错误调用从“执行”变为“报错”。
- D3：执行前确认覆盖哪些命令模式（rm -rf、systemctl stop/restart、覆盖写等）？是否接受 Agent 多一轮确认？
- D4：是否允许修改生产的 systemd unit 以使用凭据文件，以及执行窗口？
- D5：每张卡的开发者分配（建议：OPT-01、02、06、07 由 Claude；OPT-03、04 由 GPT 或 Claude，待定）。
- D6：与 T-20261016-03（RikkaHub-1，同样修改 internal/mcp 与 internal/api）的先后顺序。

## 六、验收与回滚

通用验收（每张卡都必须满足）：
- gofmt、go vet、go build 通过；go test -race -shuffle=on 连跑三次通过。
- sh docs/process/check-task.sh 通过。
- 每个行为改动都有能在还原时变红的测试（反向验证）。

回滚：所有卡只在分支上开发，合并前不影响生产。生产变更（OPT-08）必须先在演练环境验证，并保留旧版本二进制与数据库备份，按 deploy-hub-local.sh 的流程回滚。

## 七、流程约束

- 开发者只改任务卡允许的路径；不 push、不打 tag、不部署，除非 OPC 对具体步骤单独批准。
- 所有 git 写操作使用 dev-git。
- 审核与终签由 Hark 完成；代理审核的结论需标注“待 Hark 复审”。

## 八、风险

- tools/list 哈希基线：OPT-01 会改变内容，需要同步更新测试常量，否则测试失败。
- 行为变化：OPT-03、OPT-04 会让一部分历史调用失败。应先统计近 7 天的审计，确认影响范围，再上线。
- 生产变更：OPT-08 涉及 systemd 与密钥，误操作可能导致 Hub 无法启动。必须有演练和回滚步骤。
