# 并发槽整改方案（定稿，2026-11-11）

状态：定稿，待 OPC 确认派发。
范围：每令牌并发 exec 槽（默认上限 2）导致的限流。
基线：见 docs/plan/rate-limit-remediation-plan.md 开头（2026-11-08 至 11-10 共 67 次 429，全部 Dave-1）。

## 一、问题
每个令牌同时在跑的 exec 达到上限（默认 2）后，后续 exec 被拒绝，客户端表现为 429。上限是 Hub 启动时读取的全局环境变量 VPS_COMMANDER_TOKEN_EXEC_CONCURRENCY，运行中不可改，面板没有入口。异步 job（exec_start）在整个运行期间占槽，长命令（race、全量构建，60–125 秒）同样占槽。

## 二、已核实的事实
- 上限全局、默认 2，启动读一次（cmd/hub/main.go）；面板与 API 无修改入口。
- 生产未设置该变量，运行默认值。
- 异步 job 占槽直到结束（exec_jobs.go start → acquireTokenExec）。
- 异步 job 的并发拒绝不写审计（exec_jobs.go:171）；MCP 路径（mcp_adapter.go:90–91）与 REST 路径（rejectTokenExecLimit）会写 rate_limited 审计，且与速率拒绝共用同一文本，无法区分路径。
- 2026-11-08 至 11-10：67 次 429，全部 Dave-1。部分记录的 jsonrpc_method 为 notifications（速率路径），部分为空（并发或 REST 路径），需要阶段 1 的字段区分。

## 三、根因
1. 槽位被长时间占用（长命令与异步 job）。
2. 上限不可在线调整（只能全局改环境变量并重启）。
3. 拒绝不可见（异步 job 无审计；响应无占用信息；文本无法区分路径）。
4. 客户端被拒后重试，放大竞争。

## 四、目标
- 单通道撞槽次数显著下降（以 journal 429 计数，按绝对日期比较）。
- 每次并发拒绝可查：上限、当前占用、占用者、路径。
- 并发上限可在面板按令牌修改，立即生效，不重启。
- 长任务不占交互槽。
