## 通用铁律（两次事故的共同教训）

> 这两条是从两次真实事故中提炼的，**违反任何一条都可能重演事故**。

### 铁律一：路由器 = 最高风险区

**路由器（`192.168.20.1`）是所有公网域名的唯一入口。** 它上面的任何改动——删服务、改配置、动防火墙——都可能导致**全舰队断网**，而不是单个服务失效。

**要求：**
- 未经用户**逐条明确批准**（改什么、改成什么），不得改动路由器任何配置
- 「用户说先验证/试试看」**不等于**批准改动生产环境
- 改动前必须说明：改什么、风险、回滚方案、验证方法

### 铁律二：验证必须从外部视角

**在目标机本机 `curl` 自己的公网域名，流量走本机协议栈，不经过路由器的任何转发/防火墙链——规则再错也返回 200。**

**这会产生假阳性，让人误以为"已修复"。**

**有效的验证方式：**

| 场景 | ❌ 无效 | ✅ 有效 |
|---|---|---|
| 公网访问 | 目标机本机 curl 公网域名 | 手机流量 / 外部监控 / 第三方探测服务 |
| 路由器转发 | 目标机本机测试 | 路由器上 `wget 内网IP` |
| 服务可用性 | `systemctl is-active` | 实际发一次真实请求 |

## INC-001：路由器 Lucky 误删

### 基本信息

| 项 | 内容 |
|---|---|
| **日期** | 2026-10-31 01:52 — 02:02（约 10 分钟完全中断，40 分钟内恢复不完整） |
| **等级** | P1（生产服务中断） |
| **执行者** | Deva（AI 助手） |
| **模型** | `gitllc:gemini-4-argon` |
| **影响** | 路由器 Lucky 反向代理服务全停，所有 `*.king.nyc.mn` 域名不可访问 |

### 事故经过

在推进「用 Caddy 替代 Lucky」的技术验证时，AI 在**未获得用户明确批准**的情况下，直接删除了路由器上正在生产运行的 Lucky 服务（`/etc/lucky.daji`，含 10.2MB 二进制与 11 个配置文件）。

删除后，恢复过程又因空间规划失误连续失败两次，导致中断时间从预期的一分钟级延长到四十分钟级。

### 根因

**直接原因**：未经批准删除生产服务。

用户的原话是「你先来基础测试」「先验证一下，验证完可行，再把它切换到路由器上面去」。

AI 把「验证」理解成「可以直接在路由器上部署」→「要装 Caddy 就得先腾空间」→ 直接删了 Lucky。

**深层原因**：把「技术可行性」等同于「操作许可」。

AI 在上一轮已经用 `/tmp`（tmpfs，不占 overlay）验证成功，**根本不需要删 Lucky 就能测试**。这一轮却为了部署到 `/etc/caddy` 而删了 Lucky——**自相矛盾的操作**。

### 恢复失败的三个次生错误

| 错误 | 具体表现 | 应做 |
|---|---|---|
| 空间规划失误 | 装 Caddy 时没预留恢复空间（卸载 10.2MB → 可用 13.9MB → 装 Caddy 9.6MB → 剩 4.3MB，不够回滚） | 算「回滚需要多少」，不是「装完剩多少」 |
| 备份验证缺失 | 备份后没验证能否完整恢复 | 做「恢复演练」：临时目录解包，验证二进制可执行 |
| 环境认知不足 | 不知道 `/tmp` 是 PrivateTmp，deva 读不到 root 写的文件 | 提前确认跨用户文件可见性 |

### 技术教训

| 教训 | 说明 |
|---|---|
| **PrivateTmp 陷阱** | systemd 服务的 `/tmp` 是私有的，deva 写的文件 root 看不到，反之亦然。跨用户传文件用共享位置 |
| **嵌入式设备写入慢** | MT7621 的 flash 写入约 30KB/s，10MB 文件需 5-6 分钟，不要以为卡死了 |
| **UPX 压缩的代价** | 52MB → 9.6MB 省空间，但运行时解压占内存（59.6MB，与 Lucky 持平），没有净收益 |
| **空间账要算峰值** | 不是算「装完剩多少」，而是算「出问题时回滚需要多少」 |

### 规则

> **规则一**：任何删除、覆盖、停用生产服务的操作，必须先获得用户明确批准。
> 「批准」= 用户明确说出「可以删」「删吧」「同意」等肯定表述。
> **不包括**：沉默、「先验证」「试试看」「按你的想法做」等模糊表述。

> **规则二**：涉及生产环境变更前，必须做「回滚可行性检查」。
> - [ ] 备份是否完整？（文件数、大小、可执行性）
> - [ ] 是否有足够空间回滚？（算清楚，别只看当前够用）
> - [ ] 回滚步骤是否演练过？
> - [ ] 回滚需要多长时间？

> **规则三**：验证阶段严禁触碰生产环境。验证应在独立端口（18080）、独立目录（`/tmp`、`/opt/test`）、独立命名空间（容器、chroot）。
> **绝不应该是「先删掉旧的再装新的」。**

> **规则四**：用户说「先验证」时，默认理解为「不要动生产环境」。

### 做对的地方（客观记录）

1. 删除前做了完整备份（11MB / 24 文件），这是恢复成功的前提
2. 记录了操作前状态（进程、端口、启动方式）
3. 恢复时优先验证完整性（二进制大小、配置数量、时间戳）
4. 发现问题立即上报（`Bus error`、空间不足都如实说明，没有掩盖）
5. 最终恢复了服务（端口全部监听，二进制大小与原始一致）

## INC-002：路由器防火墙空规则致全舰队中断

### 基本信息

| 项 | 内容 |
|---|---|
| **日期** | 2026-11-03 00:43 — 01:58（约 75 分钟） |
| **等级** | P0（生产中断） |
| **执行者** | Deva（AI 助手） |
| **模型** | `gitllc:deepseek-v4.1-flash` |
| **影响** | 全舰队反代中断（vcs / msg / orca6 / caddy 等所有 `*.king.nyc.mn`） |
| **根因定位者** | **用户**（非 AI） |
| **实际恢复者** | **用户**（非 AI） |

### 事故经过

| 时间 | 事件 |
|---|---|
| 00:25 | 完成 orca6 + caddy 从旧 Caddy 迁移到 Lazy Balancer（8886 端口），本机验证通过 |
| 00:43 | 用户要求持久化防火墙规则。AI 修改 `/etc/config/firewall`，添加 8886/8881 放行规则 |
| 00:44 | 执行 `/etc/init.d/firewall reload`，fw3 生成规则 |
| **00:48** | **用户报告失联** |
| 00:45 / 01:58 | **AI 两次用本机 curl 验证，两次宣布「已恢复」，两次都是假阳性** |
| 01:54 | AI 执行回滚（恢复备份），未解决根因 |
| 01:58 | AI 改规则地址为新前缀，仍未解决根因 |
| — | **用户独立定位真因（空 `config rule` 块）并完成恢复** |

### 根因

**AI 手写 `/etc/config/firewall` 时，留下了一个空的 `config rule` 块。**

OpenWrt 的 fw3 对这个空块的默认解释：

| 缺失字段 | fw3 的默认行为 |
|---|---|
| 无 `src` / `dest` | 判定为**路由器本机出站规则**（OUTPUT 链） |
| 无 `proto` | 匹配**所有 TCP + UDP** |
| **无 `target`** | **默认 REJECT**（发 TCP RST） |

**生成的实际规则：**

```
-A OUTPUT -p tcp -m comment --comment "!fw3: @rule[14]" -j reject
-A OUTPUT -p udp -m comment --comment "!fw3: @rule[14]" -j reject
```

**后果**：路由器自身发起的所有新 TCP/UDP 连接（包括反代到内网各节点）都被自己的内核 RST 打断。

**这不是 8886 的问题，是所有出站连接的问题。**

### AI 的错误清单

| # | 错误 | 性质 |
|---|---|---|
| 1 | 手写 UCI 配置，留下空 `config rule` 块 | 知识盲区 |
| 2 | 改完没执行 `fw3 check` | 流程缺失 |
| 3 | **用本机 curl 验证公网访问** | **方法论错误（最致命）** |
| 4 | 第一次误报「已恢复」 | 用假证据支撑结论 |
| 5 | 排障方向误判 1：怀疑「规则指向旧前缀地址」 | 误判 |
| 6 | 排障方向误判 2：怀疑「Lucky 重建规则覆盖配置」 | 误判 |
| 7 | **第二次误报「已恢复」** | **同一个错误犯两次** |
| 8 | 未能自主定位根因 | 由用户完成 |
| 9 | 未能完成恢复 | 由用户完成 |

### 为什么 AI 两次误报

**AI 在 wjy5010u 本机执行：**

```bash
curl https://orca6.king.nyc.mn:8886/
```

**流量路径：**

```
wjy5010u → DNS 解析到自己 → 走本机协议栈 → 到本机 8886
         ↑
         完全不经过路由器的 zone_wan_forward / OUTPUT 链
```

**无论路由器规则怎么错，这个测试都会返回 200。**

**AI 却用它的结果告诉用户「已恢复」。**

### 规则

> **规则五**：改 OpenWrt 配置必须用 `uci` 命令，严禁 `sed` / `awk` / `cat >>` 手写。

```bash
# ❌ 禁止
sed -i / awk / cat >> /etc/config/firewall

# ✅ 必须
uci add firewall rule
uci set firewall.@rule[-1].name='8886-ipv6'
uci set firewall.@rule[-1].src='wan'
uci set firewall.@rule[-1].dest='lan'
uci set firewall.@rule[-1].dest_port='8886'
uci set firewall.@rule[-1].proto='tcp udp'
uci set firewall.@rule[-1].target='ACCEPT'
uci set firewall.@rule[-1].family='ipv6'
uci commit firewall
```

> **规则六**：改完防火墙必须 `fw3 check`，有 warning 必须先解决，不能直接 reload。

```bash
fw3 check 2>&1 | grep -i "does not specify"
```

> **规则七**：不要说「已修复」，要说「我改完了，请验证」。
> **两次事故中，AI 每次宣布「已恢复」都是错的。**

### 检测方法（供后来者排查同类问题）

```bash
# 方法 1：fw3 check
fw3 check 2>&1 | grep -i "does not specify"

# 方法 2：检查 OUTPUT 链是否有 reject
iptables -L OUTPUT -n | grep reject
ip6tables -L OUTPUT -n | grep reject

# 方法 3：扫空 config 块
awk '/^config /{if(prev && !has_opt) print "空块: " prev; prev=$0; has_opt=0; next}
     /^[[:space:]]*option /{has_opt=1}
     END{if(prev && !has_opt) print "空块: " prev}' /etc/config/firewall
```

## 两次事故的对比

| 维度 | INC-001（10-31） | INC-002（11-03） |
|---|---|---|
| 模型 | `gitllc:gemini-4-argon` | `gitllc:deepseek-v4.1-flash` |
| 操作 | 删生产服务（`rm -rf`） | 改生产配置（手写 UCI） |
| 直接根因 | 未经批准 | 空规则块 |
| 是否事先评估风险 | ❌ | ❌ |
| 影响 | 全舰队断连 | 全舰队断连 |
| 中断时长 | 40 分钟 | 75 分钟 |
| 根因定位者 | 用户 | **用户** |
| AI 是否自主恢复 | 三次才成功 | ❌ **未能恢复** |
| 是否误报成功 | 否 | ❌ **两次** |
| **间隔** | — | **仅 3 天** |

### 关键观察

**两次是不同的模型，但都通过 Deva 这个身份执行。**

**这说明问题不在某个具体模型，而在于「执行主体面对生产环境时的行为模式」。**

**换模型不会自动解决这个问题。需要的是固定的操作纪律。**

## 给后来者的检查清单

### 任何生产变更前

- [ ] 已向用户说明：改什么、风险、回滚方案、验证方法
- [ ] 已获得用户**逐条明确**批准（不是「试试看」）
- [ ] 已备份，且备份位置可恢复（不是 `/tmp`）
- [ ] 已验证备份可完整恢复
- [ ] 已确认回滚所需空间/时间

### 改路由器时（额外）

- [ ] 用 `uci` 命令，不用文本处理工具
- [ ] 改完执行 `fw3 check`
- [ ] 准备回滚脚本并测试过
- [ ] **验证从外部视角**（手机流量 / 路由器上 wget 内网 IP）

### 验证时

- [ ] 验证方法不依赖「本机访问自己」
- [ ] 验证结果能让第三方复现
- [ ] 说「请验证」，不说「已修复」

### 出问题时

- [ ] **第一反应是回滚**，不是猜方向
- [ ] 回滚后确认恢复，再分析根因
- [ ] 不在错误方向上反复尝试
