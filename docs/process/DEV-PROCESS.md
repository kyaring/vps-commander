# 开发流程与角色规范 v1.0

适用于所有项目。各项目的命令、路径、发布方式、开发者名单写在本项目的 `docs/process/PROJECT-PROFILE.md`（项目档案），本文件不写项目细节。

## 0. 流程总览
需求(OPC) → 任务书(规划) → OPC 确认 → 开发 → 提交审核 → 审核 → OPC 决定并入主线 → 构建切入生产（备份 + 健康检查 + 自动回滚）→ OPC 实测 → 关闭

状态：draft → ready → in_dev → in_review → (changes_requested ↺ in_dev) → approved → merged → deployed → verified / rolled_back / cancelled

通用铁律：
1. 一个任务只有一个开发者；同时进行的任务不得重叠同一文件或模块。
2. 任何生产变更（部署、改配置、改主机）必须 OPC 逐步批准。
3. AI 模型只用 OPC 指定的（见项目档案），不得自行切换；受限或失败如实报告。
4. 快速迭代期只提交本地主线，不 push、不打 tag、不发版；何时结束、版本节奏由 OPC 决定。
5. 密钥、令牌、密码不得出现在任务书、提交、日志、审核报告里（需要时用文字描述格式）。
6. 通知优先走事件，不靠轮询。

## 1. OPC（产品 / 实测 / 决策）
- 提需求：问题、可验收的期望结果、优先级、是否涉及生产。
- 确认任务书后才开工（ready 由 OPC 置）。
- 审核通过后决定：并入 / 部署 / 暂缓 / 打回。
- 部署后实测，给出 verified 或问题反馈。
```
【需求】标题
问题/场景：
期望结果（可验收的）：
优先级：P0/P1/P2
涉及生产：是/否
约束（不能动的东西）：
```

## 2. 规划（Hark 或其他 agent）
- 先核实现状（读代码、查生产），不凭记忆写任务书。
- 拆成可独立审核的任务。规模上限（非测试代码）：
  - flash 类执行型开发者：≤ 300 行、≤ 6 个文件
  - GPT 类开发者：≤ 600 行、≤ 12 个文件
  - 超出须拆分，或在任务书写明不可拆的理由并经 OPC 同意
- 指定开发者，检查不与进行中任务重叠；登记到任务看板。
- 交给 DevTask runner 的任务：允许/禁止路径只写真实前缀（不支持通配）；验收命令必须在项目允许命令列表内并原样照写。

任务书模板：
```
任务：<一句话标题>
编号：T-<YYYYMMDD>-<序号>
开发者：<见项目档案>
分支：基于 <分支>（<sha>），新建 <fix|feat>/<主题>
约束：不 push、不打 tag、不部署
改动范围：允许 <路径前缀…>；禁止 <路径前缀…>

一、问题
1. <现象 + 影响，附生产实例或复现方式>

二、要求
1. <具体行为，写清状态码、错误码、字段名、阈值>
不做：<明确排除项>

三、测试
1. <每条要求至少一个用例：输入 → 期望结果>

四、验收
<项目档案中的验收命令，原样照写>

五、交付
提交信息：<type>(<模块>): <英文一句话>
文档：<需要更新的文档>
完成后发完成通知，把 SHA 交给审核。
```
写法要点：问题写现象和证据，要求写可判定的行为，测试与要求一一对应；数字写死，不留"适当""合理"。

## 3. 开发者
- 从任务书指定基线开分支；DevTask 由 runner 生成 task/<id>。
- 只改允许范围；越界先问规划。
- 提交前项目档案中的验收命令全绿。
- 每个行为变化有测试；修 bug 先写复现测试。
- 不改项目档案列出的受保护路径（除非任务书明确允许）。
- 不 push、不部署、不碰生产。
```
【提交审核】任务编号
分支 / commit：
改了什么：
自测：<逐条验收命令 ✓/✗>
已知限制 / 审核重点：
```

## 4. 审核（Hark）
- 独立复跑全部验收命令，加 diff 空白检查和密钥扫描。
- 对照任务书逐条验收；查越界改动、回归、安全（鉴权、脱敏、注入、路径穿越）。
- 能实测的实测（临时实例、生产数据副本 dry-run、探针）。
- 结论三选一：PASS / PASS+建议 / CHANGES REQUESTED。
- 发审核事件，更新看板。
- 不替开发者改代码；不自行合并或部署。
```
【审核】任务编号  commit：
结论：PASS | PASS+建议 | CHANGES REQUESTED
验证：<命令 ✓/✗>
验收对照：逐条 ✓/✗
必须修改：
建议（非阻塞）：
风险说明：
```

## 5. 并入与发布（OPC 批准后执行）
1. OPC 明确批准 → 主线 fast-forward 到审核通过的 commit。
2. 按项目档案构建、预演（如数据迁移 dry-run）。
3. 按项目档案部署：先备份，健康检查，失败自动回滚；看到成功标志才算上线。
4. 通知 OPC，等待实测；更新看板。
```
【发布】<sha>  时间：
内容：
备份：
健康检查：
回滚方法：
OPC 实测：待定 / verified / 问题
```

## 6. 任务看板
- 每个项目在仓库 `docs/tasks/BOARD.md` 维护总表，每个任务一份 `docs/tasks/<编号>.md`（任务书）。
- 由规划/审核方（Hark）维护，每次状态变化当场更新。DevTask 任务另填 DevTask ID。
- 试行两三周确认字段后，以看板字段为需求开发 Hub 统一看板。

## 7. 新项目接入
1. 在新项目仓库建 `docs/process/`，放入本文件（原样）和填好的 `PROJECT-PROFILE.md`。
2. 建 `docs/tasks/BOARD.md`（空表）。
3. 若用 DevTask：在 Hub 注册项目（镜像仓库、基线分支、允许命令、允许/禁止路径），并为它起一个 runner 实例。
4. OPC 确认项目档案后开始接任务。
