一、问题
1. 现象：生产 Hub（8cbd273）审计里 notification_event_emit 的行 exit_code=202、result=error，目前 12 条，全部是投递成功的事件；被拒绝的 notification_event_emit_rejected（400）有 3 条，result=error，这是对的。
2. 原因：internal/api/notification_events.go 把 HTTP 状态码传给 s.audit（成功 202，幂等重放 200），而 internal/api/audit_exec_result.go 的 auditResultForCode 在非命令退出上下文里只把 0 当 ok，其他一律记为 "error"。
3. 影响：审计面板和按 result 统计的错误数虚高，真错误被淹没；接入方会误以为调用失败。

二、要求（数字写死）
1. 非命令退出上下文（isCommandExit=false）：code 为 0 或 200–299 时 result="ok"；1–199、300 及以上、负数时 result="error"（不变）。
2. 命令退出上下文（isCommandExit=true）行为完全不变：0 → ok，其他任何非零（包括 200、202）→ exit_nonzero。
3. 审计行的 exit_code 列保持调用方传入的原值（202 仍记 202），只改 result。
4. notification_events.go 和 internal/storage/（包括 normalizeAuditEntry 的默认逻辑）都不改，修复只放在 auditResultForCode。
5. docs/client-skill/SKILL.md 第 77 行「审计 result 含义」改为：`ok` 命令退出码 0，或非命令操作的 HTTP 状态 2xx；其余三项原样保留。
不做：不迁移历史审计行；不改审计表结构；不改其他调用方传入的 code。

三、测试
1. audit_exec_result_test.go 加表驱动用例：非命令上下文 0/200/202/299 → ok，1/199/300/404/500/-1 → error；命令上下文 0 → ok，1/124/200/202 → exit_nonzero。
2. notification_events_test.go：POST 一个合法事件得到 202，对应的 notification_event_emit 审计行 result=ok、exit_code=202；用同一个 Idempotency-Key 重放得到 200，审计行 result=ok、exit_code=200。
3. 被拒绝的事件（400）审计 result 仍是 error。
