## 一、背景
生产已于 2026-10-14 08:00:05 部署 `1152acb`（T-20261014-23），`GET /api/v1/health/assertions` 可用（HTTP 200，响应 750 字节），但 9 条断言里有 **3 条假阴性**。以下是 RikkaHub-1 在**生产实测**得到的根因：

1. **`service.active` / `service.restarts`** 返回 `ok:false`，detail 为 `service state unavailable` / `restart count unavailable`。
   根因：`internal/api/health_assertions.go:174`、`:178` 假设 `systemctl show … --property=ActiveState --property=NRestarts --value` 的输出顺序是「ActiveState 在前、NRestarts 在后」。
   生产实测该命令输出是 **`0` 在前、`active` 在后**（NRestarts 先），于是 `strconv.Atoi(strings.TrimSpace(lines[1]))` 对 `"active"` 解析失败 → 函数返回错误 → 两条断言都记 unavailable。
   实测该命令耗时仅 **15–21ms**、恒为 2 行，**与 1200ms 超时无关**；`env -i` 最小环境下同样正常。

2. **`hub.healthz_internal`** 返回 `ok:false`，detail `health check unavailable`。
   根因：`internal/api/health_assertions.go:67` 把内部健康检查写死为 `http://127.0.0.1:9521/healthz`，但 Hub 只绑 `192.168.20.132:9521`（unit 的 `-addr 192.168.20.132:9521`）。
   实测：`127.0.0.1:9521` → **000**（连接被拒）；`192.168.20.132:9521` → **200**。
   同类写死 `127.0.0.1` 的问题在 `deploy/upgrade-hub.sh`、`deploy/install.sh`、`internal/storage/storage.go`、`internal/notify/notify.go`、`internal/mcp/oauth.go` 也存在（已记在交接文档遗留里，**本卡只修断言接口这一处**）。

3. **`hub.healthz_public` 抖动**：`checkHealthz` 的超时是 **900ms**（`health_assertions.go:188`），而该探针要经 Cloudflare 访问公网 URL。同一次部署下，RikkaHub-1 实测 `ok:true (HTTP 200)`、GPT 实测 `ok:false`。

4. **为什么测试全绿却在生产失败**：现有测试全部注入假探针（`healthAssertionProbes`），**没有任何用例真正执行** `systemdServiceState()` 或真实 HTTP 自检，所以这三个真实探针的缺陷在单测里不可能暴露。

## 二、要求
1. 修 `systemdServiceState()`：**不得依赖 `--value` 的输出顺序**。改成按属性逐个取值（例如对每个属性单独调用一次 `systemctl show … --property=<P> --value`），或改用不带 `--value` 的 `Key=Value` 形式再按键名解析。保留 1200ms 超时与「取值不合法即返回错误」的防御（失败时断言记 `ok:false`，不要 panic）。
2. 修内部健康检查地址：**不得写死 `127.0.0.1`**。内部探针的目标地址必须由实际监听地址构造（可从启动参数 `-addr` 取，或把地址作为参数注入探针）。要求：在本机部署形态（绑定 `192.168.20.132:9521`）下，`hub.healthz_internal` 必须为 `ok:true`。
3. 修公网健康检查超时：把 900ms 提到对公网合理的值（**建议 5s**），并保证该条超时/失败只影响它自己，不影响其它断言与接口状态码。
4. **新增能覆盖真实探针的测试**（新文件或本卡测试文件内；**不得修改现有测试文件**）：
   - 一个**夹具用例**：用生产实测的输出顺序（`0` 在前、`active` 在后）作为输入，断言 `systemdServiceState` 能正确解析出 `active=true`、`NRestarts=0`；
   - 一个**真实探针用例**：在 `systemctl` 可用时调用真实 `systemdServiceState()` 并断言解析成功；`systemctl` 不可用时 `t.Skip`（保证换机器仍能跑）；
   - 一个用例断言内部健康检查的目标地址**由注入的监听地址构造**，而不是硬编码 `127.0.0.1`。
