## 一、问题

Agent 处理 file_write 时用 os.WriteFile 直接写目标文件（cmd/agent/main.go，case "file_write"）。os.WriteFile 会先截断再写入，中途失败、进程被杀或断电，会留下空文件或半截文件，而原文件已经丢失。同样的问题在 Hub 侧 edit_block 已经用临时文件 + fsync + rename 解决，但 file_write 没有复用这一做法。另外，新建文件固定 0644，写入密钥或 .env 时权限可能过宽。

## 二、要求

1. 新增 internal/executor/atomic_write.go，导出函数 `WriteFileAtomic(path string, data []byte, newFileMode os.FileMode) error`：
   - 临时文件创建在目标文件所在目录（名字前缀 `.vps-commander-write-`），写入后 fsync，再 rename 到目标路径，最后对目录做 fsync；
   - 目标已存在时，保留其原有权限位；目标不存在时使用 newFileMode；
   - 任何一步失败都删除临时文件，且目标文件内容保持不变；
   - 目标是符号链接时，写入真实目标文件，符号链接本身保持不变（先 filepath.EvalSymlinks，悬空链接返回错误）；
   - 目标是硬链接（nlink > 1）时拒绝写入，返回错误 `hardlinked file refused`（与 T-20261027-01 的 edit_block 保持一致，待 OPC 确认）。
2. cmd/agent/main.go 的 file_write 分支改为调用 WriteFileAtomic(p.Path, []byte(p.Content), 0644)。1 MiB 的内容上限、返回的 payload 结构（bytes 字段）保持不变。
3. 0644 是否需要改为 0600，由 OPC 决定（见「待确认」第 1 条）；在确认前保持 0644。

不做：
- 不改 Hub 侧 internal/api 的 fileWrite；
- 不改 executor 里已有的文件（edit.go 等），本卡只新增文件；
- 不改 Agent 其他 action。
