## 一、问题

1. 一次性 exec 超时可能永久挂死（internal/executor/executor.go，Local.Run）。超时后向进程组发 SIGKILL，但如果命令里的后台子进程用 setsid 脱离了进程组并继续持有 stdout/stderr 管道，cmd.Wait() 会一直阻塞，`err = <-waitCh` 永不返回，调用方挂死，goroutine 泄漏。同文件里 Session 版本已设置 `cmd.WaitDelay = 2 * time.Second`，一次性版本没有同步。
2. edit_block 会把符号链接替换成普通文件（internal/executor/edit.go，EditBlock）。读取时 os.ReadFile 会跟随符号链接读到目标内容，但最后 os.Rename 替换的是路径本身，结果是符号链接被普通文件取代，原目标文件内容不变。对 sites-enabled 这类配置是静默破坏。硬链接会被 rename 断开，同样静默。
3. read_multiple_files 整文件读入内存（internal/executor/fs.go，ReadMultipleFiles）。先 os.ReadFile 读完整个文件，再截断到 limit。读几 GB 的日志会占用大量内存。Agent 端 file_read 已经是分段读取，两端实现不一致。
4. 唯一匹配计数用的朴素 O(n·m) 查找（edit.go，countNonOverlapping / indexString）。大文件上明显变慢，且有现成的标准库函数可用。

## 二、要求

1. Local.Run 设置 `cmd.WaitDelay = 2 * time.Second`，与 Session 保持一致。命令正常退出时，若 cmd.Wait 返回 exec.ErrWaitDelay 且 ProcessState 的退出码为 0，按成功处理（退出码 0），与 session.go 的 wait() 逻辑一致。超时分支仍返回退出码 124。
2. EditBlock 写入前用 filepath.EvalSymlinks 解析真实路径：
   - 路径是符号链接时，读取、比对、写入都作用于真实目标文件，符号链接本身保持不变；
   - 符号链接悬空（目标不存在）时返回明确错误，不创建文件；
   - 硬链接（Stat 的 nlink > 1）时拒绝编辑，返回错误 `hardlinked file refused`，不写入。（待 OPC 确认，见下方「待确认」第 1 条）
   - 普通文件行为不变：权限保留、临时文件 + fsync + rename、哈希 CAS 检查、唯一匹配规则均不变。
3. countNonOverlapping 改用 strings.Count（或等价的标准库调用）；indexString 与 replaceOnce 改用 strings.Index。唯一匹配的错误信息文本保持不变（`found N matches` / `found 0 matches`）。
4. ReadMultipleFiles 改为 os.Open 后用 io.LimitReader 读取至多 limit 字节，不再读完整个文件：
   - 默认 limit、上限 1 MiB 的规则不变；
   - 截断时 FileReadItem 增加字段 `truncated`（bool，JSON 名 `truncated`，omitempty，截断时为 true，未截断不输出）；
   - 截断位置若落在多字节 UTF-8 字符中间，去掉末尾不完整的字符，保证 Content 是合法 UTF-8；
   - 读取失败的错误行为不变（Error 字段）。
