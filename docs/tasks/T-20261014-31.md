## 一、背景（生产实测，T-20261014-30 部署后）
1. 生产已部署 `610212a58fac`（含 L2-B/L2-C）。RikkaHub-1 实测发现：**HTTP 调用方每个连接都是新会话**。证据（同令牌、同客户端 IP，仅源端口不同）：
   - `curl --local-port 45873 …/api/v1/session/stats` → `"session_id":"http-3a797f04a7c81fb4d606f045ea543be6"`
   - `curl --local-port 45874 …/api/v1/session/stats` → `"session_id":"http-f2f7991aad904a95a6f827aa7c5d1daa"`
   ⇒ 会话身份把**源端口**算进去了。
2. 后果：HTTP 调用方 `POST /api/v1/session/memo` 写入后再 `GET` 读回**必然 404**（实测：写入返回 `{"key":"rv-probe-t30","bytes":18,"expires_at":…}`，紧接着 `GET ?key=rv-probe-t30` 返回 `{"error":"memo not found"}`）；`session/stats` 对 HTTP 调用方永远近似 0，`budget_warning` 也永不触发。**L2-B/L2-C 对 HTTP 调用方实质失效。**
3. MCP 调用方不受影响（会话 id 用 MCP session id）。
4. **为什么单测没抓到**：现有用例都**注入固定的 remoteAddr 字符串**（如 `192.0.2.17:1234`），从不模拟「同一调用方、不同连接/不同源端口」，所以测不出来。

## 二、要求
1. HTTP 调用方的会话身份改为 **「令牌 + 客户端 IP」**，**不得包含源端口**；MCP 调用方继续用 MCP session id（**保持不变**）。
2. 为「HTTP 会话」定义**空闲过期**：同一 (令牌, IP) 在 N 分钟（建议 **30**）无活动后，下一次请求视为**新会话**（`started_at` 重置、统计清零、便签清空）。N 用环境变量可覆盖（例如 `VPS_COMMANDER_HTTP_SESSION_IDLE_MINUTES`，默认 30）。
3. `session/stats` 与 `session/memo` **共用同一个身份函数**（避免两处口径漂移）；把该函数抽到一处并加注释写明口径。
4. **新增能抓住本缺陷的测试**（新文件 `internal/api/http_session_identity_test.go`，**不得修改现有测试文件**）：
   - 同一令牌、**不同源端口**的两次请求必须落在**同一会话**（`stats` 的 `session_id` 相同；memo 写后能读回）；
   - 不同令牌（同 IP、同端口）必须落在**不同会话**；
   - 空闲超过阈值后视为新会话（可注入时钟或把阈值调小来测）。
5. `docs/api.md` 更新会话身份口径说明（含「HTTP 按 令牌+IP、MCP 按 session id」与空闲过期规则）。
6. 反向验证：把身份函数改回「包含源端口」，要求 4 的第一条用例必须失败。
7. 不做：不改 executor、不改断言接口、不改审计字段、不新增 scope、不改面板、不改 memo/stats 的响应结构。
