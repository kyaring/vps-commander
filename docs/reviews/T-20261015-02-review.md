## 五、问题清单（定级 + 定性）

### 一般-1（返工项）`mcp_tool` 在请求体 > 64 KiB 时丢失

- **现象（可复现）**：对 `POST /mcp` 发 `tools/call`，请求体越大越容易丢 `mcp_tool`。实测边界：请求体 64,644 字节（pad 63 KiB）→ 日志有 `mcp_tool=list_devices`；65,668 / 66,692 / 102,532 字节 → 日志无 `mcp_tool` 字段。
- **根因**：`cmd/hub/main.go:145-163` 只读 64 KiB 前缀，却把这段**被截断的**前缀当完整 JSON 反序列化；请求体一超过窗口，`json.Unmarshal` 必然失败并 `return ""`。工具名其实就在前 100 字节内，是取得到的。
- **定性**：**漏记（观测缺口）**，不会误报失败、不泄露、不影响请求本身（我另测确认 >64 KiB 请求体仍完整送达处理器）。触发条件 = MCP `tools/call` 请求体 > 65,536 字节；概率中（长脚本 exec、`publish_post` 长文、大文件写入都会超过）。
- **卡上依据**：卡第二节第 1 条「MCP 请求另加 `mcp_tool`（如果能拿到工具名）」——此处工具名拿得到却没记，属于与卡的要求有偏差。
- **建议修法**：用 `json.Decoder` 流式取 `method` 与 `params.name`（不需要完整文档），或读到 envelope 闭合为止；并补一条请求体 > 64 KiB 的用例（现有 `TestRequestLogActorAndCredentialRedaction` 的夹具是 132 字节，检不出这个分支）。

### 建议-1 缺少 >64 KiB 请求体用例（测试强度）

- 现有「MCP request body was not preserved」断言在 132 字节夹具下形同虚设：反向验证 3 证明把 `io.MultiReader` 去掉后，该用例仍然 PASS。实现本身是对的（我探针确认 102,532 字节完整送达），但这条断言挡不住它想挡的变异。
- **定性**：只漏检变异，不会误报；触发条件 = 未来有人改动前缀读取逻辑；概率低。

### 建议-2 多字节截断无用例（测试强度）

- 夹具是 ASCII，反向验证 4 证明删掉 `value[end]&0xc0` 回退循环后测试不报警（实际会产生 U+FFFD 替换字符）。当前实现对多字节是正确的（6,000 字节中文截到 222 字节、74 个 rune、合法 UTF-8）。
- **定性**：只漏检变异；概率低。

### 建议-3 48 KiB 不是结构性上限

- 卡上夹具（每行 1 个长字段）实测 47,683 字节，余量仅 3%；我另造「每行 4 个长字段（命令/错误/目标/结果各 4 KiB）」的 100 行夹具，同一接口返回 **118,986 字节**。逐字段封顶（224 字节 + `…`）不约束整行大小。
- **定性**：卡上验收条目已满足（不算偏差），只是稳健性问题；若确实要硬约束，可加页级字节预算。
- **说明**：这是按卡的原夹具判定的，故列为建议而非一般。

### 建议-4 鉴权前读取请求体（资源/DoS）

- `POST /mcp` 现在在**鉴权之前**读最多 64 KiB 并做一次 JSON 解析；服务端只有 `ReadHeaderTimeout=10s` 与 `IdleTimeout=90s`，**没有 ReadTimeout**，而令牌限流在鉴权之后。未鉴权客户端可慢速送 body 占住 goroutine 与 64 KiB 缓冲。
- **定性**：拒绝服务面小幅扩大（概率低、影响小，生产在反代之后）；可在读取前先要求 `Authorization` 头存在，或给 body 读取加读期限。
