## 2. 判断不一致的三处（重点）

### 分歧 A：定级——SV-02 问题 2（git-credential 用户名被打码）
- 你：一般。Hark：阻塞。
- Hark 的理由：
  1. 你给的定性是「功能不可用 / 误认证」。定性已经是不可用，定级却写一般，两者自相矛盾。
  2. git-credential 是 v1 首批平台（GitHub、Gitea）的核心交付路径，带用户名绑定的凭据**一定会**认证失败，不是偶发。
  3. 这是返工引入的回归，而且违反了任务书第 12 条的明文要求（「注入时照常使用原文」）。
- 规则（以后按这个定级）：满足下面任意一条就是**阻塞**——核心功能不可用；安全或泄露问题；违反卡上的明文要求；返工引入了回归。「不影响请求本身、只少一条观测数据」这类才是一般。
- 自检方法：写完定性之后，回头问一句「这个定性和定级配吗」。

### 分歧 B：找根因——T-02 一般-1（mcp_tool 丢失）和建议-4（鉴权前读请求体）
- 你：分成两条，修法给的是「用 json.Decoder 流式解析」。Hark：合成一条，修法是「删掉鉴权前读请求体，改由 MCP 处理器在鉴权之后回填工具名」。
- Hark 的理由：两条都出在同一段代码（requestMCPTool）上。流式解析只修好了丢失这个症状，鉴权前读 64KiB 的问题还在。把这一步挪到鉴权之后，两个问题一起消失，也不用再额外读一遍请求体。
- 规则：发现两个问题在同一个函数或同一条路径上时，先想清楚「能不能一个修法同时解决」；修法优先去掉成因，而不是给症状打补丁。安全类问题（这里是鉴权前就消耗资源）不要只当建议放着，要看它和必改项是不是同一个根。

### 分歧 C：结论——SV-03 下 CR 还是 PASS
- 你：CR（一个待裁定，加一个一般：交付说明没写验收第 1 条的结果）。Hark：PASS。
- Hark 的理由：
  1. 结论衡量的是**交付物的质量**。6 条必改全部实现、测试到位，你自己也确认了这一点。
  2. 唯一过不去的验收第 1 条是 Hark 写卡写错了：长分支没合进过 main，不带参数跑 check-task 会把整个 v1 的差异都算进来。卡面缺陷不能算开发者的缺陷，也不能拿来当 CR 的依据。
  3. 「交付说明漏写」属于留痕问题。前提本身就做不到的情况下，最多是建议，不足以要求整轮返工（返工会让开发者白跑一轮）。
- 应该怎么做：
  1. 结论写 `reviewed-pass`，同时附上待裁定项，交给 Hark 裁定。
  2. 更好的做法是**自己先做替代核查**：`git diff --stat <上一轮tip> <新tip>`，看本轮增量是否全在允许范围内，把结果写进报告，Hark 就可以直接裁定。
- 规则：问自己「如果我是开发者，按这份 CR 要返工的到底是什么？」答案只是补一句话、或者改正卡的错误，那就不该下 CR。
