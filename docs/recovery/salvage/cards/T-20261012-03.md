一、问题
1. 现象：Hub 审计里 notification_event_emit 行 exit_code=202、result=error。自 2026-10-11 19:30 至 2026-10-12 16:07 共 58 条，全部是投递成功的事件（error_msg 为 "severity=P3 matched_tasks=1"）。
2. 原因：internal/api/notification_events.go 把 HTTP 状态码传给 s.audit（成功 202，幂等重放 200），而 audit_exec_result.go 的 auditResultForCode 在非命令退出上下文中只把 0 当 ok，其余一律 "error"。
3. 影响：审计面板和按 result 统计的错误数虚高，真错误被淹没；新接入 agent 的操作者会误以为调用失败。

二、要求（数字写死）
1. 非命令退出上下文（isCommandExit=false）：code 为 0 或 200–299 时 result="ok"；1–199、300 及以上、负数时 result="error"（不变）。
2. 命令退出上下文（isCommandExit=true）行为完全不变：0 → ok，其他任何非零（含 200、202）→ exit_nonzero。
3. 审计行的 exit_code 列保持调用方传入的原值（202 仍记 202），只改 result。
4. notification_events.go 本身不改；修复集中在 auditResultForCode。
5. 若 docs/client-skill/SKILL.md 或 docs/mcp-clients.md 描述了审计 result 取值，同一提交更新为新规则；没描述则不改。
不做：不迁移历史审计行；不改审计表结构；不改其他调用方传入的 code。

三、测试
1. auditResultForCode 表驱动：非命令上下文 0/200/202/299 → ok，1/199/300/404/500/-1 → error；命令上下文 0 → ok，1/124/200/202 → exit_nonzero。
2. notification_events_test.go：POST 一个合法事件得到 202 后，对应 notification_event_emit 审计行 result=ok、exit_code=202；带同一 Idempotency-Key 重放得到 200，审计行 result=ok、exit_code=200。
3. 被拒绝的事件（如 400）审计 result 仍为 error。
