一、问题
1. 现象：多个开发者同时开工后，企业微信 wecom-dev 收到的「开发完成」消息不写开发者。GPT 与 workbuddy-2 共用同一个 dev-events 令牌，source 都是 agent；flash 只在摘要里埋了一个 [flash]。OPC 只能逐条对照任务才分得清。
2. 证据：notification_events 中 development-completed 外部事件 actor 均为 dev-events、source=agent；模板标题为「开发完成：{{commit}}」，变量仅 task/commit/summary。
3. 影响：消息多时无法一眼看出是谁交付、哪个项目，容易漏审或审错。

二、要求
1. development-completed 模板变为：
   - 变量：["developer","project","task","commit","summary"]
   - 标题：`【{{developer}}】开发完成：{{project}}`
   - 正文：`任务：{{task}}\n提交：{{commit}}\n摘要：{{summary}}`（与现在相同）
   即渲染后消息第一行固定是「【开发者】开发完成：项目」，下面照旧。
2. 新库：种子模板直接用第 1 条的内容。旧库：迁移时只在该行的 title_template、body_template、variables_json 三项都等于旧默认值时更新为新值；任一项被管理员改过则保持不动。迁移可重复执行、结果不变。
3. POST /api/v1/events 发 development-completed 时：
   a. developer 未传或去掉首尾空白后为空 → Hub 用调用令牌的名字填（principal 的 Name）；令牌名也为空 → 用 source。
   b. project 未传或为空 → 填 `-`。
   c. developer、project 若传入：去首尾空白后不超过 32 个字符（按 rune），且不含控制字符和「【」「】」，否则 400，复用现有 rejectNotificationEvent 审计。
   d. 自动填充只作用于 development-completed 模板，其他模板行为不变。
   e. 幂等哈希仍按客户端原始请求计算（填充前）；同一 Idempotency-Key 重放结果不变。
   f. 事件 data_json 存填充后的变量。
4. DevTask 完成通知（devtask.go 发 development-completed 处）：developer 固定为 `flash`，project 为任务所属项目名；摘要去掉开头的 `[flash] ` 前缀，其余内容（状态、标题、diff 统计、失败信息）不变。task 标签、幂等键、P2/P3 规则不变。
5. 文档：docs/client-skill/SKILL.md 与 docs/mcp-clients.md 写明发开发完成通知时必须传 developer（自己的名字，如 GPT、workbuddy-2）和 project（项目名），给出一条完整示例请求体；docs/api.md 补充 developer/project 的填充与校验规则以及 DevTask 通知使用 developer=flash。客户端 skill 版本号 +0.1。
不做：不拆分 dev-events 令牌，不改 review-completed 等其他模板，不改通知渠道和路由，不改历史事件数据，不改 scripts/emit-notification-event.py。
