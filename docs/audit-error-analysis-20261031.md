# vps-commander 审计日志报错分析报告

- **数据范围**：Hub 审计库 `audit_logs`，2026-10-13 16:33 至 2026-10-31 01:46
- **样本总量**：11,499 条命令，其中非零退出 817 条，表面失败率 7.1%
- **报告目的**：逐类分析报错根因，给后续所有 agent 立操作规范，避免重复踩坑

---

## 一、先说清一个口径问题：817 条里约 1/4 是"伪报错"

有 194 条记录的"命令"根本不是命令，而是工作流状态字符串——`task-reported`、`development-completed`、`review-completed`、`wecom-dev` 等。某些客户端把任务状态上报塞进了 exec 通道，Hub 按 HTTP 语义回了 202 / 400 / 409 / 200，被统计成了"报错"。

- gpt-notify 的 114 条记录 **100%** 是这类（task-reported ×79、development-completed ×26）
- RikkaHub-1 的 review-completed ×49、hark-2 的 review-completed ×24

**剔除伪报错后，真实命令失败约 620 条，真实失败率约 5.4%。** 以下逐类分析针对真实失败。

---

## 二、逐类分析

### 第 1 类：失败后原样重试 —— 289 条（占真实失败约 46%，第一大浪费源）

同一 actor 把**一字不改**的命令重复提交 ≥2 次且都失败，共涉及 289 条记录。典型：

- Dave-1 的 `sleep 90; journalctl -u caddy ...` 连发两次，都是超时
- gpt-2 的 heredoc 构建脚本连发 4 次，同样的错
- 事件上报类在无确认机制下反复重发（与伪报错叠加）

**根因**：失败后不先诊断、不改任何变量，靠重试碰运气。命令的失败原因（超时、语法、环境）不会因为重发而消失，重试只是把浪费乘以次数。

### 第 2 类：执行超时（exit 124）—— 128 条

- 其中至少 36 条是 **sleep 轮询**：`sleep 75/90/120/150` 后接一条检查命令，总时长撞上 Hub 单命令约 125 秒的上限直接被杀
- 其余为构建、打包、装包（pnpm build、apt-get、go test -race 等）前台直跑超过时限

**根因**：用"睡一觉再看"代替状态确认；长任务不后台化。RikkaHub-1 早期最严重（曾过配约 5 倍轮询），Dave-1 近期仍在犯（等证书签发 sleep 90）。

### 第 3 类：pkill -f 把自己杀掉（exit -1）—— 31 条（exit -1 共 44 条）

典型（均出自 Dave-1）：

- `pkill -f "caddy run --config ..."`、`pkill -f "socat TCP-LISTEN:18443"`、`pkill -9 -f "codex login"`

**根因**：`pkill -f` 按完整命令行匹配，而匹配串就写在自己这条命令里——执行这条命令的 shell 自身的命令行包含该字符串，于是**先把自己杀了**，Hub 只能记到 -1（无结果回传）。这是纯机制问题，与目标进程无关。

### 第 4 类：复合命令拼接错误（exit 2）—— 73 条

典型：`sleep 75 echo "=== 证书状态 ===" ...`（sleep 后漏了分号，echo 被当作 sleep 的参数）；引号不配对；多层 heredoc 转义损坏。

**根因**：超长单行复合命令要穿过 JSON → shell →（ssh → shell）多层转义，写的时候没自检，错一处全盘皆错。

### 第 5 类：一般失败（exit 1）—— 296 条，最大类，需再分

| 子类 | 规模 | 根因 |
|---|---|---|
| grep 无匹配 | ≥59 条 | 命令以 grep 结尾、查无结果时 grep 返回 1。多数是**良性**的（"没找到"本身就是答案），但污染了失败统计 |
| Python 补丁锚点未命中 | 多发于 gpt-2、RikkaHub-1 | 用 heredoc 里的 patch 脚本改文件，old 字符串与文件现状对不上直接抛异常。**改前没读文件当前内容** |
| 空命令 | Dave-1 有 9 条命令体为空 | 客户端拼装 bug，提交了空字符串 |
| 真实业务失败 | 其余 | 测试不过、文件不存在等——这是正常的"干活失败"，占比不高 |

### 第 6 类：不探环境就下命令（exit 127）—— 23 条

典型：

- 在没有 Docker 的 wjy5010u 上执行 `docker ps -a`（RikkaHub-1）
- 在 BusyBox 路由器上找 `miniupnpctl`（gpt-2）
- PATH 里还没有 pnpm 就调用（claude-2，后自行补装）

**根因**：凭假设认为目标机装了某软件，不先跑一条探针确认。

### 第 7 类：SSH 姿势错误（exit 255 / 127 中的 ssh 类）—— 16 条

典型：

- ssh 192.168.20.180 不带 `-i /root/.ssh/id_vchub_180`，裸连被拒（gpt-2、grok-1 多次）
- root 直登 FNAS——服务端策略明确拒绝，kyy + 密钥才是正道，仍有人反复试 root
- 试图经 ~/.ssh/config 别名直连不可直达的节点（claude-2 连 hwsg）

**根因**：不用舰队既定约定（专用密钥 + BatchMode + 跳板），每次靠默认配置试错。

### 第 8 类：git 状态冲突（exit 128）—— 13 条

集中在 grok-1：`git worktree add -b ...`、`git checkout -b ...` 时分支或 worktree 已存在，git 直接 fatal。

**根因**：建分支/工作树前不查 `git branch --list` / `git worktree list`。

### 第 9 类：出墙网络裸连超时（exit 28 ×9、exit 35 ×2）

典型：wjy5010u 上 curl 外部地址超时、WS 探测超时。

**根因**：这台机裸连出墙被 DNS 污染 + SNI 拦截，且 Hub exec 是**非登录 shell**，不加载 `/etc/profile.d/dev-proxy.sh`——命令里不显式带 `-x socks5h://192.168.20.189:1070` 就必然超时。此坑 Muse 本人在 10-23 也栽过一次。

### 第 10 类：长尾（各 1–7 条）

exit 7（curl 连不上目标，7 条）、143（SIGTERM 被终止，2 条）、3 / 4 / 22 / 31 / 45 / 52 / 97 等工具自身失败码。量小、无统一模式，不立规范，按个案处理。

## 四、给后续 agent 的操作规范（红线清单）

1. **状态上报不许走 exec 通道。** `task-reported` 这类字符串不是命令。Hub 的失败统计只应包含真命令。
2. **禁止原样重试。** 同一命令失败后，重发前必须先跑一条诊断命令、或至少改掉一个变量；同命令同参数连续失败 2 次即熔断，停下来报告。
3. **禁止前台 sleep 轮询。** 等待一律用"短命令查状态"循环，单次 sleep 不超过 10 秒且不进同一条命令；预计 >60 秒的任务一律 `nohup` 后台 + 日志文件，之后用短命令读日志。
4. **禁止裸用 `pkill -f`。** 先 `pgrep -af` 列出目标 PID、确认不含自身 shell，再按 PID kill；服务类进程一律走 `systemctl stop`。
5. **不熟悉的机器先探针。** 第一条命令永远是 `command -v <工具>; uname -a; head -2 /etc/os-release` 这一类，确认环境后再干活。
6. **SSH 只用舰队约定姿势。** `ssh -i /root/.ssh/id_vchub_180 -o BatchMode=yes`；FNAS 用 kyy（+NOPASSWD sudo），禁止试 root 直登；不可直达的节点走跳板，不要试 config 别名碰运气。
7. **改文件先读后写。** 打补丁前必须读目标文件当前内容确认锚点存在；超过 3 层转义的长脚本，先在本地写成文件检查一遍再传输落盘，禁止在 exec 里现拼 heredoc 长脚本。
8. **出墙命令显式带代理。** `curl -x socks5h://192.168.20.189:1070` 或先 `export https_proxy=...`，不要指望登录 shell 的 profile（Hub exec 不加载）。
9. **git 建分支/worktree 前先查。** `git branch --list <name>`、`git worktree list` 确认不存在再建。
10. **grep 预期可能无结果时加 `|| true`。** 让"查无"回归为正常结果，不要污染失败统计。

## 五、流程优化建议（给 Hub / 客户端维护方）

1. **Hub 侧拦截事件字符串**：exec 入口对纯标记字符串（无空格的短标识符）直接返回提示，不落审计，避免伪报错继续产生。
2. **审计统计分口径**：失败率只统计真命令；202 / 200 类事件记录单独归档。
3. **客户端加重试熔断**：同一命令指纹（actor + 命令哈希）连续失败 ≥2 次时，客户端应强制插入诊断步骤或上报人工。
4. **Hub 返回超时预警**：命令执行超过 60 秒时在结果里附"建议后台化"提示，帮新 agent 尽早学会第 3 条。
5. **新 agent 上岗先读本报告**：本报告应作为舰队 agent 的入职材料，与各节点的环境档案（哪台有 docker、哪台走哪个代理、SSH 密钥路径）一起发放。
