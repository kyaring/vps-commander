# Muse VM 宿主机使用规范（节点 muse-01）

> 适用对象：经 vps-commander Hub 借用 Muse 所在 VM 的使用者与 agent（OPC、deva 及其他持令牌的客户端）。
> 本机由 Muse 担任监督方：负责 agent 存活、自动恢复与资源告警；任务的发起与执行不经过 Muse 会话。
> 版本：2026-11-12 修订版（Muse 著，基于 2026-11-10~12 实测；本次修订新增 §5 构建任务须知，并按实测更新重建频率与交叉引用）。

## 1. 这台机器是什么

| 项 | 值 |
|---|---|
| Hub 节点名 | **muse-01**（Hub 的 `device_credentials` 与此名绑定，改名即 401，禁止改） |
| VM 主机名 | htch-runtime |
| 形态 | 容器型 VM，跑在 88 核 AMD EPYC 宿主机上，与其他租户共享硬件 |
| 接入方式 | vps-commander-agent v1.1.36（systemd 服务 `vps-commander-agent`）+ 本地 WebSocket 中继 `vps-agent-relay`（见 §6） |
| 资源份额 | CPU 约 1.5 核共享（可见 4 vCPU；单核约比 wjy5010u 的 i3-5010U 快 30%）；内存上限 6 GiB |

这台机器同时是 Muse 助手本体的运行环境。借用算力可以，但它不是一台闲置 VPS——下面的规范就是为了让两边互不伤害。

## 2. 存储规范（最容易踩的一条）

机器有两块“盘”，口径完全不同：

| 位置 | 总量 | 可用 | 说明 |
|---|---|---|---|
| 根文件系统 `/`（含 `/opt`、`/tmp`、`/etc`） | 7.5G | 约 7.5G | overlay，**只够放系统件，禁止堆数据** |
| 家目录 `/home/hatch` | 150G | 约 147G | 专属 btrfs 卷，Muse 全部文件目前只用约 1.1G |

规则：

1. **所有工作文件一律放在 `/home/hatch/workspace/` 下**（自建子目录）。在根目录、`/opt`、`/tmp` 写大文件会迅速撞上 7.5G 上限。
2. **VM 会被平台不定期整体重建**：除家目录外的一切（`/opt`、`/etc`、已装软件、运行中的进程）全部清空，毫无预兆。2026-11-12 凌晨接连发生两次，实测每茬 VM 寿命约 1–2 小时量级（见 §5）。
   - 重要产物及时落家目录；长任务必须能断点续跑，不要假设进程能活过夜。
   - agent 与中继服务本身由看门狗在重建后自动恢复（见 §8），无需人工重装。
3. 家目录的 147G 是宿主卷的可见余量，不是独占配额；真要存放几十 GB 级数据，先小规模试放验证再批量搬。

## 3. 内存的正确读法

- **不要信 `free` / `/proc/meminfo` 的百分比**：本机 `/proc/meminfo` 是宿主整机口径（未按容器隔离），常年显示已用 90% 以上——那是同宿主其他租户的占用，与本机无关。面板里 muse-01 上报的内存数字同理，会一直“看着很高”。
- 判断本机真实用量，看**进程 RSS 合计**或 cgroup 口径。2026-11-12 实测基线：全部进程 RSS 合计约 366Mi，其中 Muse 本体运行时（`hatch` 进程）约 337Mi、WS 中继约 18Mi、agent 本体约 6.5Mi。
- 本机内存硬上限 6 GiB。借用方的任务应把自身峰值控制在约 5 GiB 以内，给 Muse 本体留出底噪；打满会触发 OOM，误伤范围包括 Muse 本体和 agent 自己。

## 4. CPU 与任务礼仪

1. 并发克制：编译类任务并行度控制在 `-j2` 量级；1.5 核共享算力下开满并行只会互相拖慢，还会拖慢 Muse 本体的响应。
2. 长任务放后台（`setsid nohup ... &` + 日志文件），用轮询日志的方式看进度；**禁止用 `sleep` 长轮询占用 Hub 的 exec 连接**——每令牌 exec 并发默认只有 2 槽，占满后该令牌的其它命令会被直接拒绝（Dave-1 在 wjy5010u 上已有多次前科）。
3. 单条 Hub exec 超时上限 300 秒；预计更久的活必须按上一条后台化。
4. 不要在这台机器上跑全盘扫描、`du` 遍历家目录之类的重型 IO 操作（家目录是网络化的 btrfs 子卷，全量遍历很慢且影响 Muse 本体）。

## 5. 构建任务须知（构建可能被中途重置——必读）

经 Hub 从其他接入端向本机下发构建指令时，**构建跑到一半被整机重置是真实且已发生的风险**，不是理论假设：

- 2026-11-12 凌晨实测：VM 连续两茬的寿命分别约 1 小时 54 分、约 1 小时 08 分。重置毫无预兆，正在运行的进程当场全灭，没有收尾、没有通知；Hub 侧那条 exec 只会看到连接断开/报错。
- 经验口径：单个构建步骤 10–20 分钟内大概率能跑完，但不打包票；40 分钟以上的单步构建在上述节奏下基本是掷骰子。

在本机做构建，必须按“随时会断”组织：

1. **一律后台化**：构建命令用 `setsid nohup <构建命令> > build.log 2>&1 &` 启动，日志与完成标记（如 `build.done` / 退出码文件）都写在**家目录工作区**里；发起方用短命令轮询标记判断成败。禁止把长构建塞进单条 Hub exec（300 秒上限之外，被重置打断时也无从判断进度）。
2. **工作区与缓存全部放家目录**：源码、产物、工具链缓存都落在 `/home/hatch/workspace/` 下（Go 的 `GOPATH`/构建缓存默认在家目录，已由 `env.sh` 配好）。这样重置只杀进程、不丢进度。
3. **靠增量续跑，不要追求一口气跑完**：Go 的构建缓存命中后，重发同一条构建命令只补被打断的包和链接环节，损失通常只有几分钟。大构建按包/按模块拆成多个短步骤分段执行，每步落标记；断在哪步就从哪步重发。
4. **产物及时固化**：编出的二进制/制品一生成就留在家目录工作区（天然持久）；需要交付到其他机器的，尽早传走，不要攒到最后一次性导出。
5. **选机原则**：本机适合短中型、迭代频繁的增量构建（缓存热起来后每轮很快）；一次跑半小时以上的大构建、全量冷编译，优先放 wjy5010u、hwsg 这类不会被平台替换的机器，本机不做此类任务的主力。
6. 构建期间发现节点掉线：先等一个看门狗巡检周期（节点恢复中）；恢复后**先查工作区的日志与完成标记**确认构建死在哪一步，再决定重发，不要盲目从头再跑一遍。

## 6. 网络出口规范

本机出网被沙箱接管，与普通 VPS 完全不同：

1. **唯一出口是 HTTP 代理**：`http://hatch-egress-proxy:3128`。交互式 shell 已通过 `/etc/environment` 和环境变量（`http_proxy`/`https_proxy`/`all_proxy`）配好；自启服务、cron、systemd 单元**不会**自动继承，需要显式写进服务环境。
2. TLS 由沙箱 CA 重签：证书校验需信任 `/run/hatch/egress-tls/ca-bundle.pem`（环境里已设 `SSL_CERT_FILE`、`CURL_CA_BUNDLE` 等）。自带证书库且不读这些变量的程序（如部分 Go/Java 程序）会出现证书错误，需单独配置或用其 insecure 选项前先评估。
3. **裸 TCP 直连不可用**：对任意地址直连 connect 会“假成功”，随后收到明文拦截提示。任何基于直连的端口探测、连通性结论在这台机器上都无效。
4. **长连接 WebSocket 经代理有已知坑**：代理链会使 Go gorilla 客户端的握手校验失败（`websocket: bad handshake`），而 Python websockets 客户端可正常完成。agent 之所以能上线，是因为本机跑了一个本地中继：agent 只连 `wss://127.0.0.1:18443`，由中继（`vps-agent-relay.service`）再连 Hub 转发帧。新增长连接程序前，先用目标客户端小规模实测握手，不要假设“curl 通了它就通”。
5. 出站目标无白名单限制（GitHub、Google 等经代理可达，出口为代理侧地址）；入站无任何端口对外开放，外界只能经 Hub 触达本机。

## 7. 红线（不要动的东西）

1. 不要停止、禁用或改配置：`vps-commander-agent.service`、`vps-agent-relay.service`，以及 agent 的 systemd drop-in（`10-egress-proxy.conf`、`20-relay.conf`）。
2. 不要改 `/home/hatch/workspace/vps-agent/` 下的持久化包（`persist/`、`restore-agent.sh`、中继脚本与证书）——VM 重建后看门狗按它恢复，改坏等于断供。
3. 不要重启 VM、不要 `systemctl` 批量启停其他服务；本机 systemd 里除上述两个服务外都是 Muse 运行时的底座。
4. **任何密钥、令牌、密码不得经 Hub 命令传递**（审计日志明文留痕）；凭据走面板/保险库的既有通道。
5. 节点改名、换凭据、升级 agent 版本属于变更，先知会 Muse（监督方），不要自行重跑 install.sh——本机安装路径与普通 VPS 不同（多了中继这一层），重跑会把连接改回直连 Hub 而再次断线。

## 8. 监督与故障处理

- 看门狗 cron `muse-vm-agent-watchdog` 每 30 分钟巡检：运行恢复脚本、核查两个服务状态与 Hub 设备列表中 muse-01 的在线状态；健康时静默，发生自动恢复或恢复失败时向 OPC 报告。
- 使用者发现 muse-01 不在线或任务异常：先等一个巡检周期（≤30 分钟，大概率已自愈）；仍异常则找 Muse 排查，不要自行重装。
- 资源告警（负载、内存触线）由 Muse 采样后主动通知；使用者无需在本机另装监控（装了也会随重建消失）。

## 9. 速查

| 问题 | 答案 |
|---|---|
| 活儿放哪 | `/home/hatch/workspace/<你的目录>` |
| 磁盘能用多少 | 家目录约 147G；根目录只有 7.5G，别碰 |
| 内存能用多少 | 上限 6 GiB，自留峰值 ≤ 约 5 GiB |
| 编译并行 | `-j2` 量级 |
| 构建会不会被打断 | 会。VM 实测约 1–2 小时一换，进程当场死；按 §5 后台化+增量续跑组织 |

| 进程过夜 | 不保证，VM 随时重建；产物落家目录、任务可续跑 |
| 面板内存 90%+ | 宿主口径，别慌；真实占用约 0.4G 起 |
